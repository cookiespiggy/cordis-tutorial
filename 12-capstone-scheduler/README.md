# 第 12 课：综合实战 —— 定时任务调度器

## 本课目标

把前面所有知识**串成一个可运行的小系统**：服务（09）、依赖注入（06）、事件系统（03）、副作用与生命周期（04）。

做一个 `SchedulerService`：插件向它注册定时任务；服务卸载时，所有定时器**自动清理**——形成完整的生命周期闭环。

## 运行

```bash
npm install
npm start
```

预期输出（时间会不同）：

```
[scheduler] 已注册任务 "heartbeat"，间隔 500ms
[2026-...] 心跳正常
[tick-logger] 任务 "heartbeat" 触发了一次
[2026-...] 心跳正常
[tick-logger] 任务 "heartbeat" 触发了一次
...（约 1.6 秒内的多次心跳）...
--- 即将卸载 scheduler 服务，验证定时器被自动清理 ---
[scheduler] 所有任务已停止（定时器已清理）
程序结束
```

卸载 `scheduler` 服务后，心跳不再出现，证明定时器被 `effect` 清理逻辑回收了。

## 要点

- **服务即能力中心**：`SchedulerService` 把「调度」这种通用能力封装成一个命名服务，供任意插件复用。
- **注入声明依赖**：`heartbeat.inject = ['scheduler']` 表达「我依赖调度器」，Cordis 保证调度器就绪后才激活该插件。
- **事件解耦**：任务每次执行通过 `ctx.emit('tick', name)` 广播，`tickLogger` 只监听事件、不依赖服务——生产者与消费者解耦。
- **副作用自动回收**：`ctx.effect(() => () => this.stopAll())` 是关键——服务所在的 fiber 被 `dispose()` 时，清理函数自动运行，避免定时器泄漏。这是 Cordis「效果即资源」思想的体现。
